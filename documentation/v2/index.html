Game Track · Blueprint v2 · 19 Sep 2026 · Neo's decisions folded in

Three games, two AI tools, one kit

Blueprint v1 asked seven questions. Neo answered them on 19 September. This version folds the answers in: Codex Astra and Claude Code work together the way they did on police sentri : RUSH, every game passes one review gate that Neo can bypass, the Mac mini build farm joins the fleet at the Kenwingston office, and every student signs consent, an IP licence and an NDA at enrolment. The first job is to build the kit and test it on ourselves.

Short version
  1. ToolsTwo AI tools, one kit. Codex Astra is the student's design and game-building partner. Claude Code is the backbone: project memory, builds, publishing, the review gate and the prompt record. This is the split that shipped RUSH to Google Play and the App Store in September.
  2. Three gamesUnchanged. Two small games, then one final game. Genres from a menu, one per slot. Confirmed 8 Sep.
  3. PublisherTodak Studios brand, on the Studios store accounts. The student signs an IP licence at enrolment. If a game earns money, the student gets a share. The percentage is still to be set.
  4. Review gateEvery game goes through one AI reviewer that assists three people: the lecturer, Neo for Todak Studios and Lan for Todak. Neo can bypass the gate to publish first. Updating a game that is already in the store is part of the course.
  5. MachinesClassroom is the Academy's Windows PCs. The Mac mini build farm sits at the Kenwingston office with the NAS, tr-home and EdgeXpert, on the fleet network. Neo is buying it.
  6. PaperworkThree signatures at registration: consent to record every prompt, the IP licence with the profit share, and an NDA. The pipeline students will see is not public knowledge.
  7. First jobBuild a working kit and test it on ourselves. No student touches it until one reference game per slot has gone through it with the review gate switched on.

Not prompt-only. Not vibe coders. AI writes a lot of the code in this course, and learners are taught to direct it well. That is not the finish line. A graduate can open their own game with the AI switched off, read the code, explain why it works, fix it when it breaks, and ship it to a store. The AI is the pair, not the pilot. Prompting is a skill we teach and grade. Understanding what comes back is the skill that makes it worth anything.

How we hold that line

  • Weekly walkthrough. The learner explains their own game's code to the mentor with the AI closed.
  • No-AI debugging drills from week 4, matching "debugging as a real skill" in the module spec.
  • The prompt journey must show growth, from "make me a game" to precise, informed direction. Prompt quality is graded, not just the game.
  • The final game is defended in a short viva, and every game passes the review gate in section 06.

02

Two tools, one kit

Neo's question: integrate Codex Astra into the kit, or run Astra as its own platform for designing and building the game, with Claude Code as the back end? Answer: one kit that both tools read, with the jobs split the way RUSH proved they should be. That gives us the "separate platform" feel for the student without building a platform.

What RUSH proved

police sentri : RUSH is a 3D chase game in a Malaysian pasar, built in Godot for phones. Between 15 and 16 September 2026 it went from a native prototype to a live game on Google Play, and was submitted to the App Store the same afternoon, all under the Todak Studios accounts and driven entirely from the fleet. Two AI tools did it, in the same repository, each on its own jobs:

Astra (Codex) did

  • Art direction, the app icon and cover art, and a screenshot plan.
  • The store listing copy in English and Malay.
  • On ApaNakMakan two days later: a full user-interface redesign delivered as a code branch, which Claude Code reviewed, tested and merged.

Claude Code did

  • The Godot prototype itself: cameras, chase and hide-and-seek modes, controls, phone builds.
  • The iPhone and Android builds, the uploads with the Studios keys, screenshots, pricing, availability and the review submission.
  • Every record: the publishing runbook, decisions, playtest notes and the handover, so any session could pick it up.

The lesson is not "Astra is creative, Claude is technical". It is that the split worked by job, inside one repository, with one tool briefing the other in writing and one tool holding the keys. That is exactly what the kit has to package for a student.

Integrated or separate? Both, in this order

Cohort 1 · one kit, two tools on the same PC (recommended)

  • The student opens Astra to design and build, and Claude Code to build, publish and review. Both read the same kit instructions, the same repository and the same project memory.
  • Weeks to build. Codex reads an AGENTS.md file and Claude Code reads CLAUDE.md; the kit writes both from one source.
  • Claude Code can fire Astra for a creative job without the student switching windows, the way it did for the RUSH store listing.
  • Both lanes are recorded. Claude Code's built-in telemetry is the most complete record available in any tool today, and Astra's session transcripts are already being collected into our brain across the fleet.

Later · Astra alone on the student PC, Claude Code as a service

  • The student only ever sees Astra. Build, publish, review and memory run on the farm as services that Astra calls.
  • Becomes possible once the kit's backbone commands are proven, because they are the same commands either way.
  • Worth doing if cohort 1 shows students struggling with two windows, or if we want a weak-laptop option.
  • Not a rebuild. The backbone moves from the PC to the farm; the lanes stay the same.

The one part not yet proven: Astra writing the gameplay code of a Godot game with a beginner. On RUSH, Claude Code wrote the gameplay; Astra's code work so far is the ApaNakMakan interface. The dry run in section 11 tests exactly this before any student depends on it.

03

What is in the Game Kit

One installer sets up both tools, the engine and the kit. From then on the student types plain requests and the kit does the plumbing. Everything below is a command any tool can fire, which is what keeps the "later" option open.

  • Start a game. "New endless runner called Sky Dash" scaffolds a Godot 4 project from the genre template, opens the student's project memory, and registers the game with the Studios publisher desk (name, package id, placeholder icon, privacy page).
  • One instruction file, two readers. The kit writes the same course rules, week, game and conventions into the file Codex reads and the file Claude Code reads, so both tools know where the student is and what the lanes are.
  • Project memory. The persistent brain from the module spec: design decisions, code conventions, bugs, all remembered across 12 weeks. Claude Code owns it; Astra reads it.
  • Assets. Sprites, tilesets, 3D models, rigs, music and sound effects through Academy-hosted services, the same image-to-3D, rigging and voice pipeline Todak runs in production. Students never hold raw API keys. Every generation is logged and metered.
  • Build and publish. "Build for web" or "push to Android testing" sends the job to the build farm and returns a link. No Xcode, no Android SDK on the student's machine.
  • Review. "Review my game" runs the AI reviewer from section 06 and files the report to the classroom system.
  • Update. "Ship version 1.0.1" bumps the version, writes the what's-new notes, rebuilds and pushes an update to a game that is already in the store.
  • Guard rails. Hooks that log every prompt, remind both tools which week and which game the student is on, and block destructive commands.
  • Helpers. A playtester agent that runs the game headless and reports what broke.

Dry-run rule, now stricter. We build the kit, then push one reference game per slot through it and publish them under Todak Studios, with the review gate on. RUSH is re-run through the kit as the capstone reference so the kit packages the exact steps that got RUSH out. Every step that breaks gets fixed in the kit before a student sees it.

The three rules

  1. Three families, not three of the same. Action, Puzzle and Strategy, Narrative, Simulation. A student's three games come from at least two different families, and the final game changes camera or dimension from games 1 and 2.
  2. If it goes to a phone, it has touch controls. Runners, racers, puzzles and sims are naturally mobile. The mentor steers the capstone choice with that in mind.
  3. Every game ships complete. Title screen, how-to-play, win and lose states, sound, and a saved high score or progress. Small and finished beats big and broken.

Not in 12 weeks: online multiplayer, open worlds, anything needing a server the student runs. Local two-player on one screen is fine.

What being under Todak Studios means, now decided

  • Publisher of record: Todak Studios, under its own brand. No separate "Academy Games" label.
  • The student keeps authorship. At enrolment they sign an IP licence that lets Todak Studios publish, market and update the game and use its design and characters. Section 09 lists what the licence must cover.
  • If a game earns money, it is split three ways: 50% Todak Studios, 20% Todak Academy, 30% the student. Decided by Neo on 20 Sep (v2.1). The split goes into the IP licence in section 09.
  • Naming rule is fixed in the kit before anyone publishes, because a package name can never change after the first upload: com.todakstudios.academy.<game>. RUSH itself is com.todakstudios.policesentrirush.
  • Credit. The student's name goes on the store listing and in the game's credits screen.

Things that bite, already known

  • Godot web games need two security headers on the hosting site. The showcase sets them and itch.io has a tick-box for it.
  • Apple's developer agreements must be accepted or the store keys stop working for days. This blocked the Studios account for months earlier this year. Check before each cohort's capstone week.
  • Every store listing needs a privacy policy page before the first submission. The kit generates one per game, the way todakstudios.com hosts RUSH's.
  • Google Play's first upload for any new app has to go through the console by hand before the automated path works. The publisher desk batch covers this.
06

The review gate, and teaching updates

Decided 19 Sep: all three games pass one review gate. An AI reviewer does the legwork and assists three people: the lecturer, Neo for Todak Studios and Lan for Todak. Neo can bypass the gate to publish first. Because games can be published first and fixed after, updating a live game becomes a lesson, not an accident.

Student says "publish"The kit builds the game and runs the AI reviewer: the store checklist, a headless playtest, the "ships complete" rule, content rating, AI disclosure and the privacy page.
→
One-page reportFiled to the classroom system with a pass, a fix list, or a block. The lecturer, Neo and Lan see it there. Any of them can send it back with notes.
→
Approve, or Neo bypassesOn approval the farm publishes with the Studios keys. Neo can publish first and let the review land afterwards, and the student ships the fixes as an update.

Why Neo's bypass is a feature

  • Google Play approved RUSH about 20 minutes after submission. Web and itch.io are instant. A blocked-but-working game teaches nothing while it waits for three calendars to line up.
  • The App Store takes longer and can reject, so the bypass matters most for web, itch.io and Play. The AI reviewer still runs; the bypass only skips the wait for human approval.
  • Every bypass is logged with who used it and why, so the record of the game still shows what the review said.

Updates are part of the course

  • Week 12 requires at least one update to a game that is already published: a version bump, what's-new notes, a rebuild and a push through the same lane.
  • Students learn what a store update actually involves: Play's staged rollout, Apple's update review, why a package name and signing key are forever, and what a hotfix is.
  • The review gate runs on updates too. The report compares the new build against the last one.

Recording every prompt, in both lanes

Three layers as in v1, now covering both tools. Nothing exotic to build; the work is the collector, the database and the lecturer's view.

Student PCClaude Code's built-in telemetry streams prompts, replies, tool calls, tokens and lines of code. The kit copies Astra's session transcripts the same way. Kit hooks add cohort, game, week and commit.
→
Course databaseEvery event stored per student and session, whichever tool it came from. Git history on the Academy's GitHub organisation sits beside it as the tamper-proof timeline.
→
Lecturer viewA Prompt Journey per student inside the classroom system: timeline per game, both lanes side by side, how specific prompts became week by week, tokens and cost, replay of any session.

Layer 1 · Claude Code's own telemetry

Claude Code can export a stream of events to any server we name. The kit installer switches it on. With the content flags set, each event carries the full prompt text, the full reply, every tool call with file paths, the model used, tokens and cost, lines added and removed, commits, the session id and the student's login email.

CLAUDE_CODE_ENABLE_TELEMETRY=1
OTEL_LOG_USER_PROMPTS=1
OTEL_LOG_ASSISTANT_RESPONSES=1
OTEL_LOG_TOOL_DETAILS=1
OTEL_EXPORTER_OTLP_ENDPOINT=https://telemetry.course.neotodak.com

Layer 1b · Astra's transcripts

Codex keeps a full transcript of every session on the machine it runs on. Our fleet already copies those transcripts into the Todak brain, which is how RUSH's Astra sessions are on record today. The kit's collector does the same for each student, tagged with the same login and session ids.

Layer 2 · the kit's hooks

On every prompt and at the end of every turn, the kit writes a row to the course database with the context the tools do not know: which cohort, which game, which week, the current commit. The same hook reminds both tools where the student is in the course, so the answers stay on the curriculum.

Layer 3 · Git

Every student game lives in the Academy's GitHub organisation. Commit history is the tamper-proof timeline. The lecturer view links prompt to commit to build to review report to published game.

What the lecturer sees

The Academy's classroom system already has students, classes, enrolments, progress and AI grading. We add a prompt-history table and a Prompt Journey page per student. The existing AI grading scores prompt quality weekly, so the student gets a growth chart at graduation and we get proof for marketing that the course teaches prompting, not just games.

Rules that come with it

  • Consent at enrolment under Malaysian data protection law, as one of the three documents in section 09.
  • Students see their own journey. Lecturers see their class. Exports and deletion on request, within what the NDA and the IP licence allow.
  • A student can technically switch recording off on their own laptop. The answer is a course rule, not a lock: work with recording switched off on purpose does not count as evidence, and the Git history stays either way. A recording fault is different: the Workbench shows "saved" or "waiting to upload" at all times, and a fault gets recovery, never a penalty (v2.2, on Astra's advice). If cohort 1 shows this being gamed, the "later" option in section 02 puts the backbone on our server and makes the record unavoidable.

Build the kit first, test it on ourselves

Neo's item 5: build a working kit and test it before anyone else does. The order below puts the risk first. Cohort 1 is not scheduled until the gate at the bottom is passed.

  1. Game Kit v1, two lanes · 2 weeks. The installer, the shared instruction file for both tools, genre templates for every menu entry, the memory wiring, the backbone commands (new game, assets, build, publish, review, update), the logging hooks.
  2. Reference game 1 through the kit · 1 week, overlapping. One of us plays the student: Astra designs and builds a game-1-sized 2D game, Claude Code scaffolds, builds and publishes it to the web and itch.io under Todak Studios. This is the test of the one unproven part, Astra writing Godot gameplay with a beginner.
  3. Review gate · 1 week. The AI reviewer, the one-page report into the classroom system, the approve and bypass buttons for the lecturer, Neo and Lan, and the bypass log.
  4. Prompt collector and Prompt Journey · 1.5 weeks. Collector for both tools, prompt table in the classroom database, the lecturer page, the weekly prompt score.
  5. Studios publisher desk · 1 week. The manifest queue, the batch checklist for creating store records, the naming rule, the per-game privacy page.
  6. Build farm · 1 week after the Mac mini arrives at the office. Until then, tr-home does Android and web builds for the dry run.
  7. Reference game 2 and RUSH as reference 3 · 2 weeks. A game-2-sized project through the kit to Play internal testing, and RUSH re-run through the kit's publish and update commands so the capstone path is the RUSH path.
  8. Showcase gallery · 1 week. Every student's three games playable on course.neotodak.com, with the required web headers.
  9. Paperwork to the lawyer · start now. Section 09 is the brief. Needed back before the enrolment form goes out.
  10. Windows lab image and home installer · 3 days. One image for the classroom PCs, one script for laptops at home.

Gate before cohort 1: one reference game per slot published under Todak Studios through the kit, with the review gate on and a full prompt record for both lanes, plus observed trials with four to six real beginners (added in v2.2 on Astra's advice: the reference games prove the pipeline, the beginners prove the teaching). If any of those four is missing, the kit is not ready and the cohort waits.

Timeline, restated in v2.2. Astra reviewed this list on 20 Sep and called the two-week kit "covering every genre" not credible. Adopted: about two weeks to a demonstrator, then six to ten more to a dependable pilot, ten to twelve weeks in all. Genre templates are built for the dry-run games first; the rest of the menu grows cohort by cohort. Details in Classroom v1, section 06.
