Game Track · Blueprint v1 · 8 Sep 2026 · Draft for Neo & Lan

Three games, one kit, every prompt on record

How students build and publish three games with Claude Code, what the classroom and home machines need, how publishing runs through Todak Studios from day one, and how we capture each student's prompting from the first lesson to the final game.

Short version
  1. ToolUse Claude Code itself, not a platform we build. Ship a Todak Game Kit that installs into Claude Code in one command and carries the whole pipeline. Our own platform is a later phase, only if cohort 1 proves students need a browser-only option.
  2. Three gamesTwo small games, then one final game. Two weeks for game 1, three for game 2, five for the capstone. Each student picks their genres from a menu, one from each family. Confirmed 8 Sep.
  3. PublishingConnected to the Todak Studios store accounts from the first lesson, through the kit. Every game goes live on the web the day it is finished. Android and PC from game 2. Google Play and iPhone TestFlight for the capstone. App Store release optional.
  4. MachinesClassroom is the Academy's high-spec Windows PCs, which cover everything except iPhone packaging. One Mac mini build farm does iPhone builds and store packaging for everyone. At home, any 16 GB laptop.
  5. RecordingClaude Code's built-in telemetry ships every prompt, reply, tool call, token count and line of code to a server we control, tagged with the student's login and session. Add the kit's own hooks and Git history and the lecturer gets a per-student Prompt Journey.

02

Claude Code direct, or a platform built on it?

Recommendation: Claude Code direct for cohort 1, with the kit carrying everything a platform would have carried. Build the platform later only if the evidence says students need it.

Claude Code + Game Kit (recommended)

  • Weeks to build, not months. The kit is skills, hooks, tool connections and templates in one package.
  • Students graduate with the real industry tool on their CV, not a wrapper only we use.
  • Claude Code improves every month for free. A wrapper always trails it.
  • Runs on the lab PC or the student's own laptop, in class or at home.

Our own platform (phase 2, if needed)

  • Browser-only. Works on a Chromebook or a weak laptop.
  • Recording happens on our server, impossible for a student to switch off.
  • One bill for AI use, metered per student, instead of seats.
  • Months of work, and it would still sit on Claude's agent toolkit, so the kit is not wasted.

The GPT-6 Astra question

OpenAI released GPT-6 Astra on 3 September 2026. It is strong at game creation and can host web games from a prompt inside ChatGPT, and OpenAI's coding tool Codex supports it. So the AI tool is not our moat and never will be.

The moat is what sits around the tool: the pipeline (genre templates, asset services, the build farm, the showcase), the project memory, the Studios publishing lane, and the recorded prompt journey. The kit's instructions are written in the cross-tool format that Codex, Gemini and Cursor also read, so adding a second tool later is cheap. Cohort 1 standardises on Claude Code because its plugin, hook and telemetry support is the most complete for recording. A small "Codex lane" with two or three volunteers in cohort 1 would show how much of the kit carries over.

03

What is in the Game Kit

One command installs it into Claude Code. From then on the student types plain requests and the kit does the plumbing.

  • Start a game. "New endless runner called Sky Dash" scaffolds a Godot 4 project from the genre template, attaches the student's project memory, and registers the game with the Studios publisher desk (name, id, placeholder icon, privacy page).
  • Project memory. The persistent brain already in the module spec: design decisions, code conventions, bugs, all remembered across 12 weeks.
  • Assets. Sprites, tilesets, 3D models, rigs, music and sound effects through Academy-hosted tools (the same image-to-3D, rigging and voice pipeline Todak already runs in production). Students never hold raw API keys. Every generation is logged and metered.
  • Build and publish. "Build for web" or "push to Android testing" sends the job to the build farm and returns a link. No Xcode, no Android SDK on the student's machine.
  • Guard rails. Hooks that log every prompt, remind Claude which week and which game the student is on, and block destructive commands.
  • Helpers. A playtester agent that runs the game headless and reports what broke, and a reviewer that checks the build against the store checklist before publishing.

Dry-run rule. Before any student touches the kit, we build three reference games through the exact pipeline and publish them under Todak Studios. Those become the course's worked examples, and every step that breaks gets fixed in the kit first.

The three rules

  1. Three families, not three of the same. Action, Puzzle and Strategy, Narrative, Simulation. A student's three games come from at least two different families, and the final game changes camera or dimension from games 1 and 2 (2D to 3D, side view to top-down, and so on).
  2. If it goes to a phone, it has touch controls. A shooter on a phone is hard to make feel good. Runners, racers, puzzles and sims are naturally mobile. The mentor steers the capstone choice with that in mind.
  3. Every game ships complete. Title screen, how-to-play, win and lose states, sound, and a saved high score or progress. Small and finished beats big and broken.

Not in 12 weeks: online multiplayer, open worlds, anything needing a server the student runs. Local two-player on one screen is fine.

Why web first, stores last

  • A web build is a link anyone can play on a phone or laptop in seconds. That is the portfolio, and it waits on no reviewer.
  • Google Play and Apple reviews take hours to days and can reject. Graduation must not depend on them.
  • The Studios organisation accounts skip the 12-tester, 14-day rule that new personal Play accounts face, so Android testing is instant.

What being under Todak Studios means

  • Todak Studios is the publisher of record for every student game. The enrolment contract has to say who owns the game and how revenue is split. The 70/30 share discussed on 3 Sep is still open.
  • A naming rule is set in the kit before anyone publishes, because a package name can never change after the first upload. Proposed: com.todakstudios.academy.<game>.
  • Whether student games carry the Todak Studios brand or a "Todak Academy Games" label on the same accounts is a decision for Neo and Lan.

Things that bite, already known

  • Godot web games need two security headers on the hosting site. The showcase sets them and itch.io has a tick-box for it.
  • Apple's developer agreements must be accepted or the store keys stop working for days. Check before each cohort's capstone week.
  • Every store listing needs a privacy policy page before the first submission. The kit generates one per game.

07

Recording every prompt

Three layers, two of them already built into Claude Code. Nothing exotic to build; the work is the collector, the database and the lecturer's view.

Student PCClaude Code + Game Kit + Godot. Built-in telemetry streams prompts, replies, tool calls, tokens and lines of code. Kit hooks add cohort, game, week and commit.
→
Course databaseEvery event stored per student and session. Git history on the Academy's GitHub organisation sits beside it as the tamper-proof timeline.
→
Lecturer viewA Prompt Journey per student inside the classroom system: timeline per game, how specific prompts became week by week, tokens and cost, replay of any session.

Layer 1 · Claude Code's own telemetry

Claude Code can export a stream of events to any server we name. The kit installer switches it on. With the content flags set, each event carries the full prompt text, the full reply, every tool call with file paths, the model used, tokens and cost, lines added and removed, commits, the session id and the student's login email. One id ties a prompt to everything it triggered, so a session can be replayed step by step.

CLAUDE_CODE_ENABLE_TELEMETRY=1
OTEL_LOG_USER_PROMPTS=1
OTEL_LOG_ASSISTANT_RESPONSES=1
OTEL_LOG_TOOL_DETAILS=1
OTEL_EXPORTER_OTLP_ENDPOINT=https://telemetry.course.neotodak.com

This works with the Claude Pro seats already in the cost model. It is a client-side feature and does not change how the student logs in or pays.

Layer 2 · the kit's hooks

On every prompt and at the end of every turn, the kit writes a row to the course database with the context telemetry does not know: which cohort, which game, which week, the current commit. The same hook reminds Claude where the student is in the course, so the AI's answers stay on the curriculum.

Layer 3 · Git

Every student game lives in the Academy's GitHub organisation. Commit history is the tamper-proof timeline. The lecturer view links prompt to commit to build to published game.

What the lecturer sees

The Academy's classroom system already has students, classes, enrolments, progress and AI grading. We add a prompt-history table and a Prompt Journey page per student. The existing AI grading scores prompt quality weekly, so the student gets a growth chart at graduation and we get proof for marketing that the course teaches prompting, not just games.

Rules that come with it

  • Consent at enrolment under Malaysian data protection law. Prompt logs are assessment evidence, which fits the competency-based portfolio the module already promises.
  • Students see their own journey. Lecturers see their class. Exports and deletion on request.
  • A student can technically switch telemetry off on their own laptop. The answer is a course rule, not a lock: work without a record does not count as evidence, and the Git history stays either way. If cohort 1 shows this being gamed, phase 2 puts a relay on our server in front of Claude Code, which keeps the Pro login and makes the record unavoidable.

Build list before cohort 1

About six weeks of work if it starts now, most of it in parallel. Items 1, 3 and 7 are where the risk lives, so they go first.

  1. Game Kit v1 · 2 weeks. Genre templates for every menu entry, the asset and build commands, the day-1 publishing manifest, the logging hooks, the memory wiring, the cross-tool instruction file.
  2. Telemetry collector + Prompt Journey · 1.5 weeks. Collector endpoint, prompt table in the classroom database, lecturer page, weekly prompt score.
  3. Studios publisher desk · 1 week. The manifest queue, the batch checklist for creating store records, the naming rule, the per-game privacy page generator.
  4. Build farm · 1 week after the Mac mini arrives. Godot exports, store uploads with the Studios keys, link back to the showcase.
  5. Showcase gallery · 1 week. Every student's three games playable on course.neotodak.com, with the required web headers.
  6. Windows lab image + home installer · 3 days. One image for the classroom PCs, one script for Windows and Mac laptops at home.
  7. Dry run · 2 weeks, overlapping. Build three reference games (one per slot) through the exact kit and publish them under Todak Studios, fixing the kit on every snag.
